# 권한 보강 — 1단계 (운영 미적용)

## pick/단골 후속 변경 (로컬 구현, 운영 미적용)

사용자 확정: pick은 본인만, 단골은 양쪽 누구나 설정/해제하는 공동 값.
`03_place_preferences.sql`은 pick만 개인별 행으로 이관한다. 단골 `is_regular` 원본은 그대로 유지한다.
같은 커플의 장소에서 본인 pick INSERT/DELETE만 가능하며 UPDATE는 금지한다.
과거 배열은 읽기 전용으로 보존하고 앱에서는 더 이상 읽지 않는다. 재실행 시 해제한 pick은 복원되지 않는다.
옛 배열의 다른 커플/존재하지 않는 프로필 ID는 새 테이블에 이관하지 않고 원본에만 보존한다.

02 적용 확인 → 03 적용 → 새 앱 배포 순서. 03 이후 구버전 pick 버튼은 오류가 나므로
점검 시간에 묶어서 적용하고 열린 탭에는 새로고침 안내. 단골 및 일반 장소 수정은 유지.
SQL 적용 없이 새 앱만 배포하면 임베딩 관계가 없어 홈/위시/상세 조회가 실패하므로 배포 금지.
현재 작업트리에는 앞 단계 온보딩 수정도 포함되어 있으므로 배포 소스 범위를 별도 확인한다.

`PGLITE_MODULE=/absolute/path/to/pglite/dist/index.js node supabase/security/test-preferences.mjs`
격리 DB 11개 시나리오 통과. 실제 두 브라우저에서 A/B가 각각 pick 선택 → 둘 다 보존,
A가 B pick 변경 불가, A 단골 설정 → B 새로고침 후 해제 → A 새로고침 후 해제 확인.
다른 커플/익명 직접 API 거부 및 실패 안내도 테스트. 실시간 구독은 이번 범위에 포함되지 않는다.

## 현재 범위

- 온보딩을 `connect_couple` RPC로 교체. 요청자의 계정 ID/이메일은 DB에서 결정.
- 생성/합류 전체를 한 트랜잭션으로 처리. 사용자 행/커플 행 잠금으로 중복 생성 및 정원 경쟁을 제어.
- 이미 연결된 사용자의 소속 이동 금지. 새 합류는 최대 2명. 기존 3명 이상 커플은 자동 삭제/분리하지 않음.
- 새 초대코드는 무작위 UUID 기반 32자. 기존 코드는 보존. 합류는 계정별 15분당 5회 제한.
- 직접 프로필 생성/소속/이메일 수정 및 커플 생성 금지. 본인 이름과 커플 시작일 수정은 유지.
- 커플 조회는 내 커플만 허용. 카테고리는 로그인 사용자 CRUD 유지, 비로그인 접근 차단.
- 기존 장소·추억·사진·커플·프로필 행은 마이그레이션에서 수정/삭제하지 않음.

## 아직 적용하면 안 되는 이유 / 사전 확인

`00_preflight_readonly.sql` 결과에서 실제 운영 함수·트리거·컬럼을 확인해야 한다.
다른 SECURITY DEFINER 함수가 profiles/couples를 임의 수정하면 이번 권한 제한을 우회할 수 있다.
미확인 함수는 전부 무작정 지우지 말고 호출처를 확인하여 제한한다.
`profiles.email`, `couples.start_date`, `my_couple_id()` 및 기존 커플 RLS가 전제다.
세 명 이상 연결된 커플은 현황만 집계하며 자동 복구하지 않는다.
신규 32자 초대코드가 실제 모바일 화면에서 줄바꿈되는지도 확인한다.

## 승인 후 적용 순서

1. 운영 DB 백업과 현재 정책/권한 내보내기. 별도 테스트 Supabase에서 아래 검증 수행.
2. `01_prepare_membership.sql`: 새 RPC 준비만 한다. **이 시점에는 기존 취약 권한이 남아 있다.**
3. 새 `OnboardingView` 코드를 테스트 배포하고 생성/합류 확인. 그다음 승인된 소스만 운영 배포.
   현재 로컬은 원격보다 58커밋 앞서 있으므로 무심코 전체 push하지 않는다.
4. 이어서 `02_enforce_membership.sql`: 기존 세 테이블 정책과 클라이언트 권한을 교체한다.
   이미 열린 구버전 온보딩은 실패할 수 있으므로 새로고침 안내. 기존 연결 계정의 데이터는 유지된다.
5. 새로고침 후 로그인/설정/생성/합류/카테고리와 직접 API 권한 확인. 실패 시 정책을 공개로 돌리지 말고 원인 수정.

구버전 UI로 되돌리면 직접 upsert가 막히므로 온보딩이 동작하지 않는다. 장애 시 신규 연결을 잠시 닫고
수정 배포하는 방식을 사용한다. 과거 `schema.sql`, `add-couple-rls.sql`, `policies_*.sql` 등 재실행 금지.
이 파일들을 재실행하면 이번 권한을 되돌릴 수 있다. 레거시 스크립트 실행 방지 장치는 후속 작업이다.

## 테스트

운영과 연결하지 않는 임시 PGlite(PostgreSQL WASM)에 최소 스키마/가상 사용자만 생성한다.
앱 의존성 변경 없이 별도 디렉터리에 `@electric-sql/pglite`를 설치한 다음:

```sh
PGLITE_MODULE=/absolute/path/to/node_modules/@electric-sql/pglite/dist/index.js node supabase/security/test-membership.mjs
```

12개 시나리오: 정상 생성·합류/정원/커플 격리/직접 수정·upsert 차단/소속 이동·중복 생성 차단/
허용된 수정/익명 차단/시도 제한/입력 검증·원자적 롤백/기존 미연결 프로필·재실행 보존/사전 점검문 실행.
추가 필수: 실제 Supabase REST/Auth/트리거 포함 검증, 독립 연결 두 개의 동시 합류·생성,
시도 제한 15분 후 해제 및 서버 오류, 브라우저 로그인/설정/새 코드 표시.
PGlite 통과는 운영 전체 안전 확인을 의미하지 않는다.

## 다음 단계: 사진

현재 저장소는 public이고 루트 UUID 파일명을 사용한다. **이번 단계에서는 사진 권한을 변경하지 않는다.**
익명 조회/업로드/수정/삭제 위험은 아직 남아 있다.

1. 기존 `places.image_url` / `memories.photo_urls`와 객체를 대조해 커플별 소유 관계를 확인.
   미참조 파일/여러 커플이 참조하는 파일은 자동 귀속·삭제하지 않는다.
2. 새 업로드 경로를 `<couple_id>/<uuid>.jpg`로 변경하고 기존 파일 이관 또는 별도 접근 매핑 준비.
3. private 버킷 + 커플 소유권 정책, 인증된 다운로드/만료되는 signed URL 도입.
   영구 저장값은 객체 경로이며 signed URL은 DB에 저장하지 않는다.
4. 목록·상세·추억·라이트박스·공유 이미지의 URL 만료/갱신까지 검증한 후 동시 전환.

카테고리는 여전히 모든 로그인 커플의 공용 데이터다. 커플별 카테고리 분리는 후속 제품 결정.
